# ADR-0056 — An ask is a message and the run it started; the rail and the column compact the same stretches

**Status:** Accepted. Implemented by `PLAN-2026-10-02-asks`. Amends
ADR-0031 (an ask whose run is long is a landmark, and a capsule never
crosses an ask) and ADR-0054 (the working mark's title names the ask).
Amended by ADR-0070: in outline, the column's last ended ask shows its
last word. Amended by ADR-0071: digests are on by default, and the user
config turns them off.
Takes up ADR-0028's sticky section header for asks. Evidence: `planChat`
(`packages/marginalia/chat.ts`) holds every message for a busy lane, and
`promptOf` (`packages/core/tree.ts`) relies on it (S21); S70
(`docs/findings/S70-asks.md`) recorded what each ending leaves.

**Context.** A thread where the agent works for a long time is hard to come
back to. Someone returning needs three things, and gets none of them
quickly:

- **Their own messages, and everyone else's.** They are spread among
  hundreds of the agent's messages and tool rows.
- **Which message the agent is working on**, and which messages are queued
  after it.
- **What the work has done so far.** Until the agent's final reply, the
  only account is the raw stream.

A column has two units, the message and the thread. What people think in
lies between the two: a message to the agent, and what was done because of
it. That unit is already in the data. A run starts from one prompt (`promptOf`:
a person's message, pi's own, a land message or a stack message), and a
lane is never written while it runs. `planChat` holds every message sent to
a busy lane, including one only for people. So no person's message ever
lands inside a run.

The rail drops the same unit. ADR-0031 treats a person's message as
uneventful, so a long agent thread compacts into one capsule, with every
message that started its work inside it. On the rail, the messages a
returning reader is looking for are the ones compacted away.

Two words are already taken. A *turn* is one agent message and its tool
results (`turnEntry`, and the revision Pineta commits after it). A *run* is
the agent's work from its prompt until it stops, and ADR-0031 also calls a
capsule a run.

**Decision.**
- **An ask is a message that started a run, together with that run.** The
  message can be anyone's: a person's message to the agent, a land message,
  or a stack message. A message for people only is not an ask. Asks are
  derived from the tree by a pure function in `packages/core`, and never
  stored. The running ask is the `promptOf` of a running lane's tip.
- **A capsule draws a stretch.** ADR-0031's capsules are called stretches
  from now on, since a run is the agent's work for one ask.
- **The column never folds a person's message. It folds the agent's part of
  a run.** A run's agent messages, with their tool rows, are one fold. A
  landmark inside the run splits the fold: a fork, the first message of a
  branch, a running tip, an open column's end, or the end of someone's
  thread. Each landmark is drawn as itself, so a fold hides content, never
  structure.
- **The rail draws the same stretches, at a coarser scale.** An ask whose
  run holds at least three agent messages (`MIN_STRETCH`) is a landmark, and its
  run is a stretch of its own, cut where the ask ends. Short asks and
  messages between people merge into stretches as ADR-0031 has it. A long
  agent thread therefore draws as one dot and one capsule per ask, and a
  chatty one stays compact. Each rail stretch is a union of whole column
  segments, folds and the messages between them. The rail may merge folds
  but never split one; the column may open a fold but never merge two.
- **A column is read at one of three densities, which the reader chooses:**

  | density | a finished ask shows |
  |---|---|
  | **outline** | its message, and one line: its outcome and its digest |
  | **story** | its message, its digest line, which is the fold, and its last word |
  | **raw** | every message and tool row, as before this ADR |

  The agent's interim text folds with the rest of the work. A message for people
  only is shown at every density. Outline lists everyone's asks, so you see
  what others ask and where they are taking the thread. A new column opens
  in story density. A column's density is kept with it in the tab's layout
  (ADR-0029), never written, and nothing changes it except the reader
  (`docs/06-interface.md`, principle 6).
- **An ask's outcome is a value, read from its run's last entries.** A
  run ends by answering, by being aborted or by failing, and pi records which
  on the entry it commits (`publishResponse`, `abortedOutcome` in pi's
  harness). A restart does not end a run: pi resumes it from the same
  prompt (S70), so it is still the same ask, and it ends as any other does.
  Every abort S70 measured came from Stop:

  | outcome | its last entries | its last word, in story |
  |---|---|---|
  | **answered** | an assistant message that stopped on its own | that message |
  | **stopped** | an assistant message with `stopReason` `aborted`, partial or empty, or a tool result cancelled before completion | what the agent was doing when it stopped: its partial text, or the cancelled call's row; nothing for an empty message |
  | **failed** | an assistant message with `stopReason` `error` | its `errorMessage` |

  So a stopped ask has no final reply, and is not drawn as if it had one.
  Its digest line says who stopped it, "stopped by Bea", from its stop
  record (below), and the column shows where the work was left, which is
  what a reader needs in order to say "go on".
- **A stop is recorded under its ask.** When Stop aborts a run (`planStop`
  returns `abort`), the host writes a `pineta.stop` value keyed by the ask's
  entry (`promptOf` the lane's tip), holding who pressed it and when. It
  writes the record before it asks pi to abort, so the record is there when
  the run's end is drawn. A record already there is kept: when two people
  press Stop together, the first one written is who stopped it. Stopping an
  idle lane writes nothing. pi's entries say that a run was aborted, never
  by whom, so the record is the only way to say who stopped it.
- **A reader opens or closes any ask's fold, at any density**, and the
  column remembers it as it remembers tool rows (ADR-0049).
- **The running ask is open in story and raw density.** While it runs, no
  one knows which of its messages will be its last word. Folding text as soon
  as it turned out to be interim would make the column shorter during a run,
  and ADR-0044 forbids that. The ask folds once its run has ended and the
  column is at its end, unless the reader opened it. At the end, what folds
  is above the view, and the column stays there with the last word in
  view. A reader scrolled up into the work keeps it open under them until
  they come back down. In outline, the running ask is one line that pulses where
  ADR-0054's working line would be. That line shows the running command
  while one is revealed, and otherwise the first line of the agent's latest
  text.
- **Anything that brings a message into view opens the fold holding it:** a
  pick on the rail, a capsule included; a mention opened from the inbox; a
  fork dot; the column header's `↰`; a branch column opening level with its
  fork point. One function makes this decision for all of them.
- **The ask stays in sight while its work scrolls.** In story and raw
  density, while the work at the top of the column belongs to an ask whose
  message has scrolled above, a bar over the column's top names it. The bar
  is laid over the content and takes no room: the follow rule reads the
  content's own height, and alignment measures offsets in it. A column that starts inside
  a run, its ask's message being in a column to its left, sticks a
  reference instead: `↰ answering Ada: "…"`. The pulsing mark before the
  thread's name names the running ask in its title: `the agent is working
  on Ada: "…"`. The column header gets no third row.
- **The digest line is counted from the run's entries:** the agent's
  messages, tool calls, the files its turns changed, its time from its
  first entry to its last, and failed calls. A capsule's tooltip is the same
  count, after the first line of its ask's message: a long ask's capsule and
  its fold hold the same messages. No branch leaves a fold: a fork is a
  landmark, drawn on its own.
- **An ask's files are the diff across its run's revisions.** After each
  agent message that changed files, Pineta commits a revision and records it
  under the entry, with the paths it changed, read with git
  (`pineta.revision`, `planTurnRecord`, `changedPaths`). So the digest's
  file count is exact as the run goes, and it is the files the review
  lists: a press opens the review pane (ADR-0047) on the range from the
  ask's prompt's commit to its last turn's. Every review is of a span, a
  revision or a range (`DiffSpan`).
- **A summary written by a model is opt-in.** With
  `{ "digests": { "enabled": true } }` in `~/.config/pineta/config.json`,
  the host asks a model for a short summary of an ask's work. The request is
  made once, outside the thread, as a commit message's is
  (`apps/pineta/host/offers/describe.ts`), and fills an `ask-digest` skill
  that the person can replace with their own. The host writes the summary as
  a `pineta.digest` value keyed by the ask's entry, as it writes
  `pineta.mark`. While the run lasts, it is refreshed at most once per
  interval, and only while someone has a column reading the thread
  (presence's `reading`, ADR-0024). It is written once more at the run's
  end, and then kept. Each write replaces the whole value, so it is a value
  and not a text (ADR-0014 is about what accumulates). It is drawn apart
  from the agent's words and titled as a summary. No agent reads a digest,
  so it puts no tokens in any context.
- **"Since you were here" marks where a reader left off.** For each thread,
  this device remembers the newest message that was drawn in a column of the
  tab you were on, as it remembers which mentions you have seen
  (`packages/client/inbox.ts`). When you come back, a line marks the first
  message after it. Read in story density, what lies below the line is the
  catch-up, and no model is asked for it.

**Consequences.**
- One segmentation in `packages/core` decides the column's folds and the
  rail's stretches, so the two cannot disagree about what is hidden. Its
  property tests check that no stretch crosses an ask, that every landmark
  stays drawn, and that the rail's boundaries are a subset of the column's.
  A mutation proves each check can fail.
- The rail grows by one dot and one capsule per long ask: about four rows
  for an ask of 10 to 99 agent messages. Each of those rows is now an ask,
  and on the rail you can now find your own messages.
- Which rail messages are landmarks now depends on a run's length. A running
  ask becomes a dot when its run reaches three agent messages, just as a
  capsule grows today only at 10, 100 and 1,000.
- In story and outline density a finished ask draws one line in place of
  its rows, which makes long threads cheaper to render (S59).
- The browser's find cannot see text inside a closed fold.
- Stops made before this ADR have no record, so their asks read as
  "stopped", naming no one.
- Turning on summaries costs a model request per interval for each running
  thread someone is reading, and one more at each run's end.
- When marks come (ADR-0028), a marked message is a landmark, and its
  section header sticks above an ask's.
- The code calls ADR-0031's runs stretches (`RailStretch`, `WorkStats`,
  `stretchWords`).

**Alternatives rejected.**
- **Separate views of the whole column (raw, files, summary) switched like
  tabs.** Switching loses the reader's place. Files and summaries belong
  beside the ask they describe.
- **A summary panel beside the columns.** It would compete with the column,
  and it would sit far from the work it summarizes.
- **One running summary of the whole thread.** It goes stale and gets long.
  The asks' digests, read in order, already make one.
- **Every ask a landmark on the rail.** A session of short exchanges would
  cost rows on every turn, which is why ADR-0031 rejected separate runs for
  agent work and conversation.
- **The rail following which folds are open.** The rail draws the tree, not
  how one reader is reading it, and it would change with every fold.
- **Folding interim text as soon as it turns out to be interim.** The column
  would get shorter during a run (ADR-0044).
- **A third header row reading "answering: …".** The sticky ask and the
  mark's title already say it, and the header would grow with every fact
  added to it.
- **Outline listing only your own asks.** In a shared thread, seeing what
  others ask is half the point.
- **One density per tab.** A reader may watch one thread raw while skimming
  another in outline.
- **Recording the stop on pi's entry.** Entries are written once by pi
  (ADR-0004), and only `packages/pi` may know their shape (ADR-0003).
- **Who stopped, kept in the stopper's client.** No one else would see it,
  and a reload would lose it.
- **The last Stop pressed winning.** The run ended at the first.
- **Summaries on by default.** They cost money and can be wrong.
- **A catch-up summary written for each reader when they return.** The
  digests below the "since you were here" line already are one.
- **"Turn" or "run" as the unit's name.** A turn is one agent message, and a
  run is only the agent's part of an ask.
